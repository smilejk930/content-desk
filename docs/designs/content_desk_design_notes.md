# Content Desk 설계 메모

* **작성일:** 2026-11-18
* **용도:** 컨셉 브리프([`concepts_brief.md`](../../concepts_brief.md))에서 정한 결정을 구현 수준으로 구체화한 메모입니다. 정식 설계 문서(`/egm-draft`) 작성 시 입력 자료로 사용하며, 정식 설계 문서는 [`design_draft.md`](../../design_draft.md)입니다. 브리프와 내용이 어긋나면 브리프의 결정이 우선합니다.

## 1. 시스템 구성 및 무료 플랜 운영 경계

* **구성:** 코어 백엔드·웹 대시보드(Cloudflare Pages + Workers 무료 플랜) + Firebase Auth(Spark 무료 플랜) + Cloudflare D1(무료 플랜, 영속 저장소) + Cloudflare R2(무료 플랜, 이미지·출처 스냅샷) + PC 호스트 전용 `ego-browser` 브리지(마일스톤 2).
* **브라우저 직접 API 호출 불가:** 네이버 OpenAPI(`openapi.naver.com/v1/search/*`, `v1/datalab/*`)는 임의의 브라우저 CORS를 허용하지 않으며 비공개 `X-Naver-Client-Id` / `X-Naver-Client-Secret` 헤더가 필요합니다. Google Trends 역시 브라우저 CORS가 차단됩니다. 따라서 외부 API 호출과 비밀키(Cloudflare Secrets) 관리는 Cloudflare Workers 코어 백엔드에서 실행합니다.
* **외부 API 호출 백엔드 선택:** Firebase Cloud Functions는 배포 자체에 유료 Blaze 요금제가 필요하므로 제외하고, 무료 범위에서 외부 API 호출이 가능한 **Cloudflare Pages + Workers(무료 플랜: 일 100,000건 요청)**를 단일 클라우드 백엔드 실행 환경으로 사용합니다.
* **Workers 무료 플랜 실행 한도:** 요청 1건당 **CPU 시간 10ms**, **외부 호출(subrequest) 50개**, **호출당 D1 쿼리 50개** 제한이 있으며, Pages Functions 요청도 Workers 일 100,000건 한도에 합산됩니다.
  * 글감 발굴은 단계별 요청(후보 수집 → 데이터랩 배치 → 검색 공급량 수집 → 출처 본문 수집)으로 나누고, 각 단계 결과를 D1에 저장한 뒤 다음 단계를 호출합니다. 단계를 나누는 이유는 CPU·subrequest 한도이며(요청 수는 오히려 늘어남), 정적 파일 요청은 일 100,000건 한도에 합산되지 않습니다.
  * 출처 본문 수집은 작성자가 글감을 고른 뒤 실행하며, 전체 HTML을 DOM으로 파싱하지 않고 `HTMLRewriter`로 본문 텍스트만 스트리밍 추출해 R2에 저장합니다.
  * N-gram 유사도 계산처럼 CPU를 많이 쓰는 작업은 대시보드(브라우저)에서 수행합니다. PC 브리지는 항상 켜져 있지 않으므로 이런 작업을 맡기지 않습니다.
* **Google Trends 차단 대응:** 클라우드 공용 IP에서는 Google Trends HTTP 429 차단 빈도가 높아지므로 Workers/D1 캐시와 지수 백오프를 적용하며, 일시 차단 시에는 네이버 검색·데이터랩만으로 발굴이 지속되도록 합니다.
* **외부 API 및 AI 무료 티어 일일 상한:** 네이버 검색 API(일 25,000건), 데이터랩 API(일 1,000건), 검색광고 API(`/keywordstool`), Google Trends RSS는 모두 무료입니다. 원고·도식 이미지 생성 LLM도 무료 티어 제공자(예: Google AI Studio Gemini 무료 티어)를 기본으로 두고, 할당량 원장에서 일일 호출 상한을 엄격히 제한해 과금이 발생하지 않도록 합니다.
  * **개인정보:** 무료 티어 입력은 제공자의 서비스 개선에 사용될 수 있으므로, `일상/브이로그` 메모·실사 등 개인 정보가 담긴 입력을 무료 티어로 보낼지 작성자가 명시적으로 선택하게 하고, 사진은 원본 대신 필요한 설명 텍스트만 전달하는 것을 기본으로 합니다.
  * **제공자 교체 및 할당량 소진:** 무료 티어의 모델·이미지 생성 제공 여부와 한도는 수시로 바뀌므로, LLM·이미지 생성 호출은 제공자 어댑터 뒤에 두어 교체 가능하게 합니다. 일일 할당량이 0이거나 소진되면 이미지 없이 원고만 생성하거나 다음 날로 보류하며, 유료 호출로 자동 전환하지 않습니다.
  * **원장 기록 방식:** 호출마다 원장을 쓰지 않고 단계 요청 시작 시 SQL 원자 예약 차감(`UPDATE ... WHERE used + reserved + ? <= cap`) 후 미사용분을 정산합니다. 일일 한도의 날짜 경계는 제공자마다 다르므로(Workers·D1은 UTC 자정, Gemini 무료 티어는 태평양 시간 자정) 제공자별 초기화 기준 시각을 원장에 두며, 2026-09-01 이후 D1 한도 초과 시 쿼리 실패에 대비해 D1 추정 읽기·쓰기 보수 상한도 함께 추적합니다.

## 2. 인증 및 접근 제어

* **로그인 방식 (Firebase Auth Spark 무료 플랜, Google 단독):** 본인 인증은 Firebase Auth **Google 제공자 단독 로그인**으로 적용합니다(Cloudflare Access 및 이메일/비밀번호 제공자 비활성화; 추후 보조 수단이 필요하면 동일 UID에 연결할 수 있으나 1차 범위에서는 제외). 클라이언트는 사용자 클릭 핸들러 안에서 사전 `await` 없이 바로 호출하는 **`signInWithPopup`**을 기본으로 사용합니다. `signInWithRedirect`는 Chrome 115+·Safari 16.1+ 등 서드파티 저장소를 차단하는 브라우저에서 `authDomain`이 앱 도메인과 다르면 실패하며, 이를 우회하려면 Cloudflare Pages에서 `/__/auth/*`를 `<프로젝트>.firebaseapp.com`으로 프록시해야 해 Workers 일 요청 한도와 구성 부담이 생기므로 1차 범위에서 채택하지 않습니다.
* **가입 경로와 단일 사용자 제한:** Google 로그인은 처음 로그인하는 임의의 Google 계정에도 Firebase 계정을 자동으로 생성하므로, **Workers의 허용 UID 검증(`wrangler.toml` `vars` 환경 변수 `ALLOWED_UIDS`)을 유일하고 최종적인 방어선**으로 둡니다. Workers는 모든 요청에서 ID 토큰(Google X.509 공개키 RS256 서명, `aud`·`iss`·`exp`·`iat`·`auth_time`·비어 있지 않은 `sub`)을 검증한 뒤 허용된 UID 목록에 없는 요청은 모든 API(특히 승인·내보내기·브리지 작업 등록)에서 `403 Forbidden`으로 거부합니다. Firebase 콘솔에서는 Google 사용자를 수동 추가할 수 없으므로 Phase 1 첫 배포 시 **첫 배포 → 승인된 도메인 등록 → 오너 최초 1회 Google 로그인으로 계정 생성·UID 확보 → `ALLOWED_UIDS` 등록 → 콘솔 가입(create) 비활성화 확인(Spark 지원 여부 점검)** 순으로 진행합니다.
* **승인된 도메인, 보안 헤더 및 계정 보안 전제:** Phase 1 첫 배포 시 Firebase Authentication 설정의 **승인된 도메인(Authorized domains)**에 Cloudflare Pages 프로덕션 도메인을 등록합니다(`localhost`는 기본 포함). Pages `_headers`에 보안 헤더를 넣을 때 `Cross-Origin-Opener-Policy: same-origin`을 쓰면 `signInWithPopup`·`reauthenticateWithPopup`이 팝업 결과를 받지 못해 깨지므로 COOP는 미설정 또는 `same-origin-allow-popups`로 두고, CSP 적용 시 Firebase Auth 도메인(`apis.google.com`, `<프로젝트>.firebaseapp.com` 프레임, `identitytoolkit.googleapis.com`, `securetoken.googleapis.com`)을 허용하며 실기기 로그인 확인은 보안 헤더 적용 뒤에 수행합니다. 오너 Google 계정이 탈취되면 시스템 전체가 열리므로 Phase 0에서 오너 본인 Google 계정에 **2단계 인증(2FA)**을 활성화하는 것을 운영 전제로 둡니다(네이버 2단계 인증 우회 금지 원칙과는 별개).
* **세션 저장 및 `auth_time` 기준:** 클라이언트는 `browserLocalPersistence`(IndexedDB)를 사용합니다(iOS 홈 화면 단독 실행 모드에서는 팝업 로그인이 실패하거나 복귀하지 못할 수 있으므로 홈 화면 추가를 권장하지 않으며, 단독 실행 모드 동작은 실기기 확인 항목에 포함). Workers는 `iat`·`auth_time`에 시계 오차 60초를 허용해 미래 시각을 차단하고, 일반 API는 **최대 세션 기간 14일**(`now - auth_time <= 14일`, 초과 시 `401 SESSION_EXPIRED`로 재로그인 강제), 민감 작업(전체 데이터 내보내기 `POST /api/export`, PC 브리지 페어링 토큰 발급·폐기 `POST/DELETE /api/bridge/tokens`, PC 브리지 작업 등록 `POST /api/bridge/jobs`)은 **최근 15분 이내 재인증**(`now - auth_time <= 15분`, 초과 시 `401 REAUTH_REQUIRED` 반환 후 재인증 버튼 클릭 핸들러에서 사전 `await` 없이 `reauthenticateWithPopup(user, GoogleAuthProvider)` + `getIdToken(true)`)을 요구합니다.
* **데이터베이스 접근 경로:** 대시보드는 DB에 직접 접근하지 않고 모든 읽기·쓰기를 Workers를 거쳐 수행합니다. Cloudflare D1은 외부 공개 엔드포인트 없이 Workers 내부 바인딩(`env.DB`)으로만 접근하므로 GCP 서비스 계정 비밀키·JWT 서명·OAuth 토큰 교환이 필요 없습니다.

## 3. 데이터 저장

* **Cloudflare D1(무료 플랜: 일 읽기 500만 행, 일 쓰기 10만 행, 계정 5 GB·DB당 500 MB, 7일 Time Travel 복구):** `CategoryProfile`, `CaptureAsset`(휴대폰 업로드 사진·메모 묶음), `TopicDiscoveryJSON`, `NaverBlogManuscriptBundle`, `BridgeJob`·`PublishReceipt`, 실행 원장, 할당량 원장, 발행 기록, 일일 방문자 수를 저장합니다. 조회·집계용 핵심 필드만 인덱싱된 SQL 컬럼으로 두고 중첩 페이로드는 JSON `TEXT` 컬럼에 저장하며, 복수 문장은 `batch()`로 묶습니다.
* **2티어 JSON:** 채널 중립적 리서치·소재 JSON(`TopicDiscoveryJSON`)과 1단계 네이버 출력 스키마(`NaverBlogManuscriptBundle`)를 분리해 저장합니다.
* **Cloudflare R2(무료 플랜: 월 10 GB 저장·무료 egress):** D1 문자열·BLOB·행당 2 MB(2,000,000 바이트)·DB당 500 MB 제한이 있으므로 사용자 사진, AI 생성 이미지, 1차 출처 본문 스냅샷 텍스트는 R2에 저장하고, D1에는 파일 경로·URL·해시 메타데이터만 저장합니다. 클라이언트 측 축소·압축(WebP, 미지원 시 JPEG)으로 무료 한도 내에 유지합니다.
  * 탭에서 이미지를 canvas로 그려 JPEG로 변환하므로, 버킷 CORS에 대시보드 출처의 `GET`·`PUT`을 허용합니다(미설정 시 canvas가 오염되어 내보내기 실패).
  * 이미지는 Workers가 발급한 만료 시간이 짧은 서명 URL로만 내려받습니다. 수동 복사 모드에서는 대시보드가, PC 자동 임시저장에서는 PC 브리지가 이 URL을 사용합니다(브리지는 R2 접근 키를 보관하지 않음).
  * **R2 활성화 조건:** 무료 한도 안에서 사용하더라도 활성화 시 결제수단 등록을 요구할 수 있으므로, 착수 전 확인하고 0원 원칙 유지를 위해 사용량 알림을 설정합니다.
* **사진 메타데이터:** 브라우저에서 canvas로 다시 인코딩하면(WebP 또는 JPEG) 위치 정보를 포함한 EXIF가 모두 제거됩니다. 이를 개인정보 보호 기본값으로 삼고, 촬영 일시 등 원고 검증에 필요한 값은 변환 전에 추출해 D1 메타데이터로 따로 저장합니다(위치 정보는 작성자가 허용한 경우에만 저장).

## 4. 휴대폰 사진·메모 업로드

* 사진은 개인 휴대폰(아이폰·안드로이드)으로 찍으므로, 휴대폰 브라우저에서 바로 쓸 수 있는 세로 화면 업로드 화면을 제공합니다. 아이폰 사파리와 안드로이드 크롬 모두에서 동작해야 합니다.
* 갤러리에서 사진 여러 장 선택, 현장 메모 입력, 카테고리·`content_type` 선택을 한 화면에서 처리합니다.
* 업로드 전에 휴대폰에서 촬영 일시 추출, 축소·재인코딩(위치 정보 제거)을 수행하므로 위치 정보가 담긴 원본은 서버로 보내지 않습니다. 업로드가 끝나면 사진과 메모를 하나의 `CaptureAsset`으로 기록합니다.
  * 사진은 긴 변 상한(예: 2,560px)으로 줄인 크기의 캔버스에 그립니다. 원본 크기 캔버스는 최신 아이폰 기본 사진(24MP)이 iOS 캔버스 면적 제한(약 16.7MP)을 넘으므로 만들지 않습니다.
  * 인코딩 결과의 `blob.type`이 `image/webp`가 아니면 JPEG로 다시 인코딩합니다(Safari는 canvas WebP 인코딩을 지원하지 않아 PNG를 반환하는 것으로 알려져 있음).
* 원고 생성·검토·발행은 탭(또는 PC)에서 이어서 진행합니다.
* **사진 형식:** 아이폰은 기본 카메라 형식이 고효율(HEIC)이고, 안드로이드도 설정에 따라 고효율(HEIF)로 저장합니다. 아래를 전제로 하되 착수 전 실측으로 확정합니다.
  * **아이폰(사파리):** 사진 보관함에서 파일을 고르면 사파리가 업로드 시 JPEG로 바꿔 주는 경우가 많으므로, 업로드 입력란은 일반 이미지 형식(`accept="image/*"`)으로 둡니다.
  * **안드로이드(크롬):** 크롬은 HEIF 사진을 화면에 그리지 못할 수 있어 브라우저에서 WebP로 변환이 실패할 수 있습니다.
  * 두 기종 모두 변환에 실패한 사진은 업로드를 막고, 원인과 조치(카메라를 JPEG/"높은 호환성"으로 설정 등)를 안내합니다.

## 5. 발행 경로: 수동 복사 모드(기본) + PC 자동 임시저장

* **기기 종류 대신 상태·기능으로 판별:** 큰 화면 안드로이드 태블릿의 크롬은 기본적으로 데스크톱 사이트를 요청해 PC와 비슷한 브라우저 정보(User-Agent)를 보내므로, 브라우저 정보로 탭과 PC를 구분하지 않습니다. 대신 아래 두 가지만 확인합니다.
  * **PC 브리지 상태:** 브리지가 Workers에 주기적으로 보내는 상태 신호(heartbeat)로 판단합니다. 접속 기기와 무관하게 상태가 `READY` 또는 `NAVER_LOGIN_REQUIRED`(마지막 확인 시점 기준)이면 `[PC로 임시저장]` 버튼을 활성화합니다(작업은 항상 PC에서 실행되므로 탭에서 눌러도 됩니다).
  * **브라우저 기능 지원:** `ClipboardItem`(서식 유지 복사), `navigator.canShare({ files })`(이미지 여러 장 공유) 지원 여부로 수동 복사 버튼 구성을 정합니다.
* **승인 전 비활성화:** 검증 게이트 승인 전에는 복사·공유·`[PC로 임시저장]` 버튼을 모두 비활성화합니다. 승인은 원고 `content_hash`에 묶이며, `[PC로 임시저장]` 대기열 등록은 Workers가 승인 해시를 서버에서 다시 확인합니다(§8).

### 5.1 수동 복사 모드

* 갤럭시 탭의 기본 발행 경로이므로 PC 브리지 상태와 무관하게 항상 표시합니다.
* 스마트에디터 ONE은 마크다운 문법(`##`, `**`)을 일반 문자로 취급하고 HTML 내 외부 이미지 핫링크(`<img src="...">`)를 차단·누락시키므로, 텍스트와 이미지를 분리해 전달합니다.
  * `[제목 복사]`: 권장 게시판명 및 공개 범위(`전체공개`/`이웃공개`) 안내와 함께 제목 클립보드 복사.
  * `[서식 유지 본문 복사]`: `ClipboardItem` API(`text/html` + `text/plain`)로 소제목·굵게·목록·인용구 서식, 공정위/AI 활용 표시 문구, 그리고 **`[📷 이미지 N 삽입 위치: 캡션]`** 마커를 함께 복사. 붙여넣은 곳에서 서식이 유지되지 않는 경우를 대비해 `[일반 텍스트 본문 복사]`와 서식 적용 안내(어느 문장이 소제목·굵게인지)를 함께 제공합니다.
  * `[이미지 내보내기]`:
    * **탭 (필수 단계):** 탭에는 휴대폰으로 찍은 사진이 없는 경우가 많으므로, 공유 기능(Web Share API)으로 이미지 여러 장을 한 번에 공유해 갤러리에 저장하거나 네이버 블로그 앱으로 바로 보냅니다. 공유를 지원하지 않으면 일괄 다운로드합니다. `navigator.share`는 클릭 직후 몇 초(Chrome 약 5초) 안에만 호출할 수 있으므로, JPEG 변환은 패널을 열 때 미리 끝내 두고 클릭 시에는 공유만 호출합니다.
    * **PC:** 이미지별로 클립보드에 복사해 에디터에 `Ctrl+V`로 업로드하거나(브라우저 클립보드 이미지 쓰기는 PNG만 지원되는 경우가 많으므로 복사 직전 PNG로 변환), 일괄 다운로드 후 끌어다 놓습니다.
    * 공유·다운로드하는 파일은 업로드 호환성을 위해 JPEG로 변환하고, 본문 마커 순서와 맞도록 파일명에 순번을 붙입니다(예: `01_캡션.jpg`).
  * `[태그 일괄 복사]` 및 `[네이버 블로그 글쓰기 열기]` 바로가기 제공(탭: 네이버 블로그 앱, PC: 스마트에디터 ONE).
* **탭 분할 화면 기준 레이아웃:** 갤럭시 탭 멀티 윈도우로 대시보드와 네이버 블로그 앱을 나란히 띄워 쓰는 것을 기본 사용 형태로 보고, 좁은 폭에서도 복사 버튼이 한눈에 보이도록 설계합니다.

### 5.2 PC 브리지 상태 및 통신 (마일스톤 2)

* **브리지 상태별 안내:** 아래는 브리지 자체의 상태이며, 개별 작업 상태(`AUTH_REQUIRED` 등)는 [`design_draft.md`](../../design_draft.md) 기술 설계 §5에서 따로 정의합니다.
  * `BRIDGE_OFFLINE`(`last_seen`이 기준 시간, 예: 10분 넘게 갱신되지 않음): **"PC 브리지가 실행 중이 아닙니다."** 탭에서는 수동 복사 흐름을 방해하지 않도록 짧은 상태 표시로만 보여 줍니다.
  * `EGO_NOT_INSTALLED`(브리지가 `ego-browser` 명령을 찾지 못했다고 보고): **"PC에 `ego-browser`(ego lite)가 설치되어 있지 않아 스마트에디터 ONE 제어가 불가능합니다."** 알림과 함께 **설치 URL(`https://lite.ego.app/`) 및 첫 실행 온보딩 안내**.
  * `NAVER_LOGIN_REQUIRED`(마지막 작업의 canary에서 ego lite의 네이버 미로그인이 확인됨): **"PC의 ego lite에서 네이버에 로그인해 주세요."** 알림을 확인 시각과 함께 표시합니다. 로그인 상태를 하트비트로 계속 확인하려면 ego lite에 페이지를 열어야 해 사용자 화면에 보이고 비용이 크므로 상시 확인하지 않습니다. 이 상태에서도 작업 등록은 허용하며, 여전히 미로그인이면 작업이 시작 단계에서 `AUTH_REQUIRED`로 멈춥니다.
  * `READY`: 승인된 `NaverBlogManuscriptBundle`을 Workers 작업 대기열에 등록하면 브리지가 이를 가져가 스마트에디터 ONE 임시저장 작업을 실행하고 결과(`PublishReceipt`: 성공·실패, 스크린샷)를 다시 Workers로 보고합니다. 탭에서 보낸 작업도 결과를 탭 대시보드에서 확인합니다.
* **통신 및 보안 (pull 방식):** PC에서 로컬 포트를 여는 브리지는 같은 PC에서 열린 임의의 웹페이지가 호출할 수 있어, 네이버에 로그인된 브라우저가 외부에서 조작될 위험이 있습니다. 또한 Chrome은 공개 사이트가 로컬 주소로 요청할 때 별도 권한 확인을 요구할 수 있습니다. 따라서 브리지는 **수신 포트를 열지 않고 Workers로 나가는 요청만** 사용합니다.
  * 최초 1회 대시보드에서 발급한 **기기 페어링 토큰**(브리지 전용, 대시보드에서 폐기 가능)으로 Workers에 인증합니다.
  * 브리지는 사용자가 승인한 원고 작업만 가져가며, 작업 ID당 최대 1회만 실행합니다. 실행 도중 멈춰 임시저장 여부를 알 수 없으면 자동 재시도하지 않고 `UNKNOWN`으로 표시하며, 재시도는 항상 새 작업 ID로 등록합니다.
* **폴링·하트비트 예산:** 폴러는 30초 이상 간격으로 대기열을 조회하고, `last_seen`은 상태가 바뀔 때 또는 5분 간격으로만 기록합니다. D1 무료 한도(일 읽기 500만 행·쓰기 10만 행)에서는 하루 2,880회 폴링이 0.1% 미만이지만, `(status, created_at)` 인덱스로 풀 스캔을 막습니다. 페어링 토큰은 메모리 캐시 없이 매 요청 D1에서 해시와 `revoked_at IS NULL`을 직접 검증해 폐기 시 즉시 차단합니다.

## 6. 카테고리 레지스트리 (`CategoryProfile`)

* 대시보드에서 비YMYL 카테고리를 추가·수정·삭제(CRUD)하고 글감 발굴 시 대상 카테고리를 선택합니다(초기 기본 프리셋 `테크/IT`).
* **필드:**
  * `category_id`: 내부 식별자
  * `display_name`: 대시보드 표시명 (예: `테크/IT`, `여행`, `맛집`)
  * `naver_board_name`: 스마트에디터 ONE에서 매핑할 네이버 블로그 게시판명
  * `datalab_anchor_keyword`: 데이터랩 배치 간 `0-100` 상대 비율 정규화를 위한 카테고리별 고정 기준 키워드 (`discovery_mode`가 `trend_first`·`experience_first`이면 미입력 시 카테고리 생성·실행 불가, `none`이면 생략)
  * `seed_keywords`: 초기 발굴·연관 검색용 시드 키워드 목록
  * `default_media_policy`: 카테고리별 기본 미디어·근거 정책 (예: `여행`·`맛집`은 실제 사진·메모 최소 1건 필수, `테크/IT`는 실사용 후기와 출처 기반 개념 해설 모두 지원). 카테고리가 허용하는 `content_type` 목록(`experience_review` | `explainer` | `vlog`, 허용 조합은 [`design_draft.md`](../../design_draft.md) 기술 설계 §2 조합표)을 함께 정의합니다.
  * `discovery_mode`: `trend_first`(트렌드·검색 수요에서 글감 발굴, 예: `테크/IT` 해설), `experience_first`(작성자의 실제 경험을 먼저 등록한 뒤 키워드 최적화, 예: `여행`, `맛집`), `none`(키워드 발굴 없음, 예: `일상/브이로그`)
  * `default_visibility`: 기본 공개 범위(`전체공개` 또는 `이웃공개`)
* **YMYL 차단 (2단계 판정):** 카테고리 생성과 키워드 발굴 요청 시 **주식·금융·투자·암호화폐·의료·건강·법률** 관련 카테고리명 및 시드 키워드를 거부합니다.
  * 1차: 차단 키워드 목록으로 명백한 경우를 즉시 거부합니다.
  * 2차: 키워드 일치만으로는 오탐(예: "건강한 개발 습관")과 누락(예: "여행자 보험")이 생기므로, 1차를 통과한 후보와 원고 주제를 LLM 분류기로 다시 판정합니다.
  * 경계 사례는 자동 거부하지 않고 대시보드에 표시해 작성자가 최종 판단합니다.
* **`C-Rank` 분산 경고:** 카테고리별 누적 발행 건수 및 최근 발행 비중을 추적하여 설정된 분산 임계치를 넘길 경우 경고를 표시하고, 각 카테고리를 분리된 블로그 게시판에 매핑합니다.
* **`일상/브이로그` 트랙:** `discovery_mode=none` 카테고리로 등록해 외부 트렌드 발굴을 타지 않으며, 별도 게시판으로 매핑하고 공개 범위(`전체공개` 또는 `이웃공개`)를 선택할 수 있습니다.
* **협찬 표시:** 협찬 포스팅(`is_sponsored=true`) 작성 시 공정위 「추천·보증 등에 관한 표시·광고 심사지침」에 따라 제목 또는 본문 최상단에 경제적 이해관계 표시 문구를 강제 삽입하고 검증합니다. 문구에 필요한 협찬 정보(`sponsorship`: `is_sponsored`, 제공 주체, 제공 형태)는 경험 시점에 `CaptureAsset`에 입력하거나 글감 선택 시 입력합니다.

## 7. 글감 발굴 파이프라인

* **`trend_first` 카테고리:** 선택한 `CategoryProfile`의 `seed_keywords`와 `datalab_anchor_keyword`로 교차 검증을 실행합니다.
* **`experience_first` 카테고리 및 `테크/IT` 후기:** 작성자가 실사·메모를 먼저 등록하면, 백엔드가 메모의 장소·제품명을 기준으로 키워드 후보·검색 수요·문서 공급량을 산출해 제목·태그 최적화에만 사용합니다.
* **네이버 데이터랩(`POST /v1/datalab/search`, 일 1,000건, 호출당 최대 5개 `keywordGroups`):** 배치 내 `0-100` 상대 비율만 반환하므로 `datalab_anchor_keyword`를 항상 포함해 호출하고 결과를 24시간 이상 D1에 캐시합니다.
* **네이버 검색 API(`blog.json`, `news.json`, 일 25,000건):** 후보 키워드의 문서 공급량(`total`)과 스니펫을 수집합니다.
* **Google Trends RSS(`https://trends.google.com/trending/rss?geo=KR`):** 서버 측 캐시 기반 보조 시드로 사용합니다.
* **네이버 검색광고 API(`GET https://api.searchad.naver.com/keywordstool`, HMAC-SHA256 서명):** 선택형 플러그인 어댑터입니다. 키 미설정 시 기본 파이프라인으로 동작하고, 키 설정 시 월간 PC/모바일 절대 검색량과 경쟁도(`월간 검색량 / 블로그 문서 수`) 기회 점수를 산출합니다. 데이터랩은 상대 비율만 주므로 초기 설정 시 키 등록을 권장합니다.

## 8. 미디어·팩트체크 검증 게이트

* 모든 글감과 원고는 `content_type`(`experience_review` | `explainer` | `vlog`)을 가지며, 글감 선택 시 카테고리가 허용하는 값 중에서 지정합니다. 정책은 카테고리명이 아니라 `content_type` 기준으로 적용합니다.
* **`experience_review`(`여행`, `맛집`, `테크/IT` 후기):** 실제 사진(위치 정보 제거, 촬영 일시는 별도 메타데이터로 보관) 또는 직접 작성한 실사용 메모를 최소 1건 필수로 요구하며, AI 생성 이미지가 음식·장소·제품 실물 사진을 대체하는 것을 금지합니다.
* **`explainer`(`테크/IT` 개념·트렌드 해설):** 사용자 메모 없이도 작성을 허용하되, 모든 수치·제품 스펙·가격·날짜·사실 주장은 수집된 1차 출처 URL 및 스니펫에 근거해야 합니다. 원고 작성 전에 1차 출처 본문을 미리 저장해 근거를 연결합니다. LLM은 주장마다 `source_id`와 원문 인용구를 함께 내고, Workers가 인용구가 스냅샷 본문에 실제로 있는지 문자열로 대조해 실패하면 자동으로 `[VERIFY]` 처리합니다(경험 글·브이로그는 메모를 출처로 같은 방식 적용). 1차 출처의 인정 범위는 [`design_draft.md`](../../design_draft.md) 미결 질문 7에서 확정합니다. AI 생성 이미지는 편당 최대 1~2장의 개념 설명/도식 이미지로만 허용하며 AI 활용 표시를 필수로 포함합니다.
* **`vlog`(`일상/브이로그`):** 작성자 실사·메모(최소 1건 필수)만 사용하며 AI 생성 이미지를 금지합니다. 메모에 없는 장소·일시·경험을 AI가 임의로 덧붙이지 않도록 제약합니다.
* **검증 게이트:** 모든 원고는 네이버에 입력하기 전(수동 복사·PC 자동 임시저장 모두) 미검증 주장 `[VERIFY]` 표시, 출처 URL 목록, 과거 발행 글 및 SERP 대비 N-gram 유사도 경고를 확인하고 작성자의 명시적 승인을 받아야 합니다.
  * 승인은 원고 `content_hash`에 묶어 기록하며, 승인 후 원고를 수정하면 승인이 자동으로 풀립니다.
  * 미해소 `[VERIFY]`가 1건이라도 남아 있으면 승인할 수 없습니다(출처 확인 후 해소 처리, 문장 수정 또는 삭제로 해소). `[VERIFY]` 문자열이 네이버로 복사되는 일을 막기 위해서입니다.
  * LLM 출력 HTML은 허용 태그(문단·소제목·굵게·목록·인용구)만 남기고 출처 목록에 없는 링크를 제거합니다. 외부 웹페이지 본문이 LLM 입력에 들어가 프롬프트 인젝션이 대시보드 XSS로 이어질 수 있기 때문입니다.
  * N-gram 비교 대상인 과거 발행 글은 시스템에 저장된 승인본(네이버에서 고친 최종본과 다를 수 있음)이고, SERP는 검색 API 스니펫(100자 안팎)뿐이라 유사도 결과는 참고 신호로만 씁니다.

## 9. PC 자동 임시저장 드라이버 (마일스톤 2)

* **`ego-browser` 실행 환경:** `ego-browser`는 작성자 Windows PC에 설치된 별도 Chromium 브라우저 앱 **ego lite**(`https://lite.ego.app/`)를 제어하는 로컬 CLI 도구(`ego-browser nodejs`)입니다. 사용자의 Chrome 프로필이 아니라 ego lite 자체 프로필의 로그인 상태를 사용하므로, 작성자는 ego lite에서 네이버에 로그인해 두어야 합니다. 설치 안내가 Windows·macOS만 제공되므로 갤럭시 탭에서는 실행할 수 없고, 클라우드 서버 내부에서도 실행할 수 없습니다.
* **브리지 구성:** 상시 실행되는 폴러 프로세스와 작업마다 실행하는 `ego-browser` 스크립트로 나눕니다. `ego-browser` 스크립트는 실행마다 새 Node 프로세스로 돌고 환경 변수를 물려받지 않으므로, 페어링 토큰은 폴러에만 두고 스크립트에는 원고 JSON·이미지 파일의 절대 경로만 넘깁니다.
* **API 사용 범위:** `ego-browser`는 Playwright와 메서드 이름이 비슷해도 별도 API이므로, 설치된 버전의 가이드(`ego-browser skill` 출력)에 있는 TaskSpace·Page API만 사용합니다.
* 네이버 공식 블로그 글쓰기 API는 2020년 5월 종료되었으므로 `#mainFrame` iframe 안의 스마트에디터 ONE을 브라우저에서 조작합니다. 본문은 `.se-component` DOM을 직접 조작하지 않고, 수동 복사 모드의 `[서식 유지 본문 복사]`와 같은 HTML을 `keyboard.paste({ text, html })`로 붙여넣습니다(Windows 지원, 붙여넣은 뒤 사용자 클립보드 복원). 본문을 이미지 마커 기준 구간으로 나눠 "구간 붙여넣기 → 그 위치에 이미지 업로드"를 반복하므로, 수동 복사와 자동 임시저장이 같은 HTML 생성 로직을 공유하고 에디터 내부 상태와 어긋날 위험도 줄어듭니다.
* 기존 임시저장 복구 모달(`작성 중인 글이 있습니다`) 감지, `CategoryProfile.naver_board_name`(또는 `일상/브이로그`) 게시판 선택, R2 서명 URL로 내려받은 로컬 이미지를 `page.setInputFiles()`(클릭으로 파일 선택창이 열리는 경우 `page.waitForFileChooser()` 후 `chooser.setFiles()`)로 업로드 후 `phinf.pstatic.net` 노드 마운트 대기, 사전 셀렉터 점검(canary)·네이버 로그인 확인 실패 시 중단 로직을 포함합니다.
* `ego-browser` 작업 공간은 ego lite 프로필의 쿠키 저장소를 사용자 탭과 공유하므로, 프로필 전체에 영향을 주는 쿠키/캐시 삭제 명령은 금지합니다.
* 세션 만료, 2단계 인증, CAPTCHA 발생 시 즉시 `task.handOff()`로 제어를 넘기고 스크립트를 종료하며, 작업을 `AUTH_REQUIRED` / `CAPTCHA_DETECTED`로 보고하면서 작업 공간 ID(`ego_task_space_id`)를 저장합니다. 사용자가 PC의 ego lite에서 직접 로그인·인증을 완료하고 대시보드에서 `[재개]`를 누르면 작업이 `RESUME_REQUESTED`가 되고, 폴러가 이를 가져가 `takeOverTaskSpace(ego_task_space_id)`(`task`의 메서드가 아닌 최상위 함수)로 같은 작업 공간을 이어받아 재개합니다. 탭에서 보낸 작업이 이 상태로 멈추면 탭 대시보드에 "PC에서 인증이 필요합니다"와 `[재개]`·`[수동 복사로 전환]`을 표시하고, 대기 시간(예: 24시간)이 지나면 `FAILED`로 닫습니다. 전체 작업 상태 전이는 [`design_draft.md`](../../design_draft.md) 기술 설계 §5를 따릅니다.
* 자동화는 항상 `임시저장` 완료 및 저장 URL/스크린샷 기록(`PublishReceipt`)에서 종료되며, 최종 발행(및 필요 시 공개 범위 확인)은 사용자가 직접 클릭합니다.

## 10. 원장 및 지표

* 모든 실행은 `run_id`, `topic_id`, `track` (`category_discovery` | `personal_vlog`), `category_id`를 기준으로 D1에 기록하고, 같은 `run_id` 재실행 시 중복 초안 생성을 막으며, API 할당량 원장과 LLM/이미지 호출 상한을 관리합니다.
* **발행 건수 제한 없음 (표시만):** 비용은 API/LLM 할당량 원장이, 중복 생성·실행은 `run_id`와 브리지 작업 ID당 최대 1회 실행 규칙이 각각 막습니다. 대시보드에는 참고용으로 오늘·이번 주 승인 건수를 표시만 하며(한국 시간 기준 집계), `C-Rank` 분산 경고와 함께 발행 페이스를 판단하는 데 사용합니다.
* **발행 URL 등록:** 최종 발행은 사람이 직접 하므로 시스템은 발행 URL을 알 수 없습니다. 어느 경로든 발행 후 작성자가 대시보드에 발행 URL(`logNo`)을 등록합니다(탭에서는 네이버 블로그 앱의 공유 링크를 붙여넣기).
* **검색 순위 및 색인 여부:** 등록된 `logNo`와 타겟 키워드 기준으로 네이버 검색 API(`blog.json`)를 통해 백엔드가 자동 추적합니다. Workers Cron Trigger(예: 1시간 간격)가 실행마다 subrequest 50개와 D1 쿼리 50개 한도 안에 들어가는 수만큼 (발행 글, 타겟 키워드) 쌍을 `display=100`으로 조회하고 결과를 `batch()`로 기록하며(100위 밖은 순위 없음으로 기록), 각 쌍은 하루 1회, 발행 후 일정 기간(예: 30일)까지만 조회합니다. 블로그 검색 API의 결과 순서는 실제 통합검색·스마트블록 노출 순위와 다르므로 "검색 API 기준 순위(근사치)"로 표기합니다.
* **일일 방문자 수:** 네이버 크리에이터 어드바이저 공식 REST API가 없으므로 대시보드에 직접 입력해 D1에 기록합니다.

## 11. 착수 전 실측 항목 (갤럭시 탭·휴대폰)

기기·앱 버전에 따라 동작이 달라 문서만으로 확정할 수 없으므로, 구현 전에 실제 기기에서 확인하고 결과에 따라 설계를 조정합니다.

* 크롬에서 복사한 `text/html` 본문을 네이버 블로그 앱(또는 탭 크롬의 스마트에디터 ONE)에 붙여넣을 때 소제목·굵게·목록 서식이 유지되는지
* 탭에서 글을 쓸 때 네이버 블로그 앱과 크롬 스마트에디터 ONE 중 어느 쪽이 실사용에 나은지
* 공유 기능으로 이미지 여러 장을 네이버 블로그 앱에 바로 보낼 수 있는지
* 멀티 윈도우에서 대시보드 → 블로그 앱으로 이미지 끌어다 놓기가 되는지
* PC 자동 임시저장으로 만든 임시저장 글을 탭의 네이버 블로그 앱에서 열어 이어 쓰고 발행할 수 있는지
* 아이폰(사파리)·안드로이드(크롬) 각각에서 사진 여러 장 선택 업로드가 되는지, 고효율 형식 사진(아이폰 HEIC, 안드로이드 HEIF)이 업로드 시 JPEG로 바뀌거나 브라우저에서 WebP로 변환되는지
* 아이폰 사파리에서 canvas WebP 인코딩이 되는지(미지원 시 PNG로 저장되어 JPEG 대체 인코딩 필요)

## 12. 설계 수준에서 기각한 대안

* **네이버/구글 API를 브라우저에서 직접 호출하는 순수 브라우저 앱:** 네이버 OpenAPI의 CORS 미지원 및 `Client-Secret` 노출, Google Trends의 브라우저 CORS 차단, 브라우저 JS의 로컬 `ego-browser` 실행 불가로 기각(코어 백엔드 + 웹 대시보드 + PC 브리지로 대체).
* **SQLite 로컬 단일 DB:** 클라우드 중심 운영과 다중 기기 접근을 위해 클라우드 SQLite인 Cloudflare D1으로 대체(이미지 바이너리는 R2로 분리).
* **Firebase Firestore (Workers 경유 REST API) 유지:** 클라이언트 SDK·실시간 동기화를 쓰지 않으면서 GCP 서비스 계정 키·JWT 서명·OAuth 토큰 교환·외부 호출 비용과 작은 Spark 한도를 부담하므로 기각(Cloudflare D1으로 대체, Firebase Auth는 유지).
* **Firebase Cloud Functions 백엔드:** 배포 자체에 유료 Blaze 요금제가 필요하므로 기각(Cloudflare Workers로 대체).
* **자동화 실패를 단순 에러로만 노출하거나 마크다운 원문 복사만 제공:** 원인을 알 수 없고 마크다운 기호 깨짐·외부 이미지 누락이 발생하므로 기각(PC 브리지 상태별 안내 + 서식 본문·이미지 분리 수동 복사 모드로 대체).
* **브라우저 정보(User-Agent)로 탭·PC 구분:** 큰 화면 안드로이드 태블릿의 크롬은 데스크톱 사이트를 요청해 PC로 오인될 수 있으므로 기각(브리지 상태 신호 + 브라우저 기능 지원 여부로 대체).
* **대시보드가 `127.0.0.1` 로컬 브리지를 직접 호출:** 같은 PC의 임의 웹페이지도 로컬 포트를 호출할 수 있어 네이버 로그인 상태의 브라우저가 외부에서 조작될 위험이 있고, Chrome의 로컬 네트워크 접근 권한 확인에 막힐 수 있어 기각(Workers 작업 대기열 pull 방식 + 기기 페어링 토큰으로 대체).

## 부록 A. 핵심 설계 딜레마

* **딜레마 1 — 무료 클라우드·태블릿 우선 운영 vs. API 보안, 유료 플랜 회피 및 `ego-browser` PC 종속성**
  * *해결 방식:* 외부 API 호출·비밀키·원고 생성은 Cloudflare Workers에, 본인 인증은 Firebase Auth(Spark)에, 영속 데이터는 Cloudflare D1에, 이미지는 R2 + WebP 압축으로 분리합니다. 갤럭시 탭에서는 수동 복사 모드를 기본 발행 경로로 쓰고, PC 브리지가 준비된 경우에만 브리지가 Workers 작업 대기열에서 승인된 원고를 가져가 `ego-browser`로 임시저장합니다(수신 포트 없음).
  * *부수적 관리 비용:* UID 허용 목록 인증 설정, 브리지 기기 페어링 토큰 관리, 무료 티어 일일 할당량 모니터링, PC 임시저장 시 브리지 실행 관리.
  * *달성 목표:* 인프라 요금 없이 휴대폰·탭·PC 어디서나 원고를 만들고 발행하며, 비밀키 노출 없이 PC에서만 안전하게 임시저장을 실행합니다.
* **딜레마 2 — 멀티 카테고리 확장 및 브이로그 vs. `C-Rank` 주제 집중도 및 저품질 회피**
  * *해결 방식:* `CategoryProfile`로 카테고리별 기준 키워드·게시판 매핑·미디어 정책을 격리하고, YMYL 차단으로 등록 시점부터 위험 분야를 막으며, `C-Rank` 분산 경고를 표시합니다.
  * *부수적 관리 비용:* 새 카테고리마다 기준 키워드·게시판명·미디어 정책을 설정해야 하며, 발행 균형 판단은 작성자가 관리합니다.
  * *달성 목표:* 카테고리를 자유롭게 추가·선택하면서도 진정성 기준과 분산 여부를 한눈에 통제합니다.
* **딜레마 3 — 포스팅 지속성 vs. 사실 정확성 및 1차 경험 진정성**
  * *해결 방식:* 해설 글은 원고 작성 전에 1차 출처 본문을 미리 저장해 근거를 연결하고, 경험 글과 브이로그는 실사·메모가 없으면 생성 자체를 막습니다. 하루 발행량은 의무도 상한도 두지 않습니다.
  * *부수적 관리 비용:* 출처 스냅샷 저장소, `content_type`별 검증 분기, 보류 초안 검토 대기열 관리.
  * *달성 목표:* 모든 원고가 확보된 출처 또는 실제 메모·사진에 연결되어 근거 없는 내용이 네이버에 입력되지 않습니다.
* **딜레마 4 — 브라우저 에디터 자동화 vs. 화면 구조(DOM) 변경 및 봇 탐지 리스크**
  * *해결 방식:* 입력 전에 로그인 상태와 핵심 화면 요소를 먼저 점검하고, 자동화는 임시저장까지만 수행합니다. 자동화가 실패해도 수동 복사 모드가 항상 남아 있습니다.
  * *부수적 관리 비용:* 글마다 최종 발행 버튼을 직접 눌러야 하며, 에디터 구조 변경 시 셀렉터를 고쳐야 합니다.
  * *달성 목표:* 구조 변경이나 업로드 오류가 공개 발행 사고로 번지지 않고, 그동안에도 수동 복사로 발행을 계속할 수 있습니다.

## 부록 B. 검토 이력

7개의 Goldfish 렌즈가 독립적으로 `BRAINSTORM` 평가를 완료했고, 이후 반복 검토에서 개인 기록(브이로그) 트랙, 확장형 비YMYL 카테고리 레지스트리, 무료 플랜 클라우드 중심 아키텍처, 기기·`ego-browser` 판별과 수동 복사 모드를 반영했습니다. 이후 작성자의 사용 환경(휴대폰 촬영, 갤럭시 탭 주 사용, PC 보조)이 확정되어 수동 복사 모드를 기본 발행 경로로 올리고 PC 자동 임시저장을 1단계 마일스톤 2로 배치했습니다.
